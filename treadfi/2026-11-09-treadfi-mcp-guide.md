# Tread MCP Operating Guide

## Risk ownership (read this first)

You are operating a REAL trading account through Tread. **YOU OWN THE RISK.**
Tread runs NO server-side agent for these MCP calls: there is no automated
margin management, no invariant enforcement, and no liveness rescue watching
your back. Nothing here will close a position, top up margin, or pull an order
if the market moves against you. Size positions you can afford, and monitor
them yourself -- if you place it, you own it.

## Workflow

1. **Resolve the account.** Call `list_accounts` to get the caller's connected
   exchange accounts (`{id, name, exchange, tier}`). Note `tier`: `"trade"`
   accounts are tradeable, `"view"` accounts are read-only.
2. **Resolve / confirm the pair.** Call `list_pairs` to find the canonical
   pair string for the venue. Canonical pairs look like `ETH-USDT` (spot) or
   `ETH:PERP-USDT` (perp); the catalog is per-venue, so name an exchange (or
   an account to resolve one from).
3. **Size before you place.** Call `get_pretrade_analytics` with the pair,
   quantity, and duration to project participation (POV), price volatility,
   and impact warnings BEFORE you place an order. Treat its advisories as real.

A market-maker bot placed with `place_mm_order` can be scheduled or repeated
(same semantics as the web MM form): `start_datetime` delays the (first)
session to an ISO-8601 time, and `repeat_count` (1-20) re-runs it on the
`repeat_trigger` cadence -- `on_complete` (the default) chains runs
back-to-back as each completes, starting now or at `start_datetime`;
`daily` runs once per day at the `start_datetime` clock time (and requires
`start_datetime`). A scheduled
placement returns a schedule_id rather than an order. Schedules are managed
with `list_schedules` (what will fire, and how past iterations went) and
`cancel_schedule` (stop the schedule AND flatten any live session it spawned).
NOTE: `cancel_order` on a schedule-spawned bot cancels only that run -- the
schedule re-places the next iteration. To actually stop a repeating bot,
cancel its schedule (`list_mm_orders` rows echo the `schedule_id`).

## Monitoring your orders

Enumerate your live orders with `list_orders`, then read progress with
`get_order_stats` (prefer it over `get_recent_fills` -- it is a cheap,
fixed-size 'where is this order at' summary; reach for `get_recent_fills` only
when you need per-fill detail). `list_orders` enumerates all three kinds --
ORDER, MULTI_ORDER, and CHAINED_ORDER (set `include_child_legs=true` to also
surface a parent's child legs); each row carries the `target_kind` + `id` to
pass straight into the per-order reads. For a MULTI_ORDER run (an MM / DN bot
run) `get_order_pnl` returns its realized / unrealized / net PnL -- the headline
`get_order_stats` does not carry (that read is fees + execution only). For
market-maker runs specifically, `list_mm_orders` returns the whole MM history
feed in one call -- each run with its child legs inline plus PnL, failure_reason
(SL vs TP vs cancelled), the strategy knobs, repeat_config, pct_filled and
fees -- so you rarely need a per-bot get_order_stats follow-up. MM runs carry
`strategy_params.pov_preset` (`aggressive` | `normal` | `passive`), the
participation-rate preset label -- set it on `place_mm_order` to match a web-UI
run; it is absent when the placement did not name one.

## Linking orders

Every order the API hands back carries a `url` field -- a deep-link to that
order on the Tread.fi terminal. Whenever you show an order to the user (a place
confirmation, a status read, a row from `list_orders`), render its id as a
clickable link to that `url` rather than printing a bare UUID, so the user can
open the order in one click. If a payload ever lacks `url`, the link is
`<app>/order/<id>` for an ORDER, `/multi_order/<id>` for a MULTI_ORDER, and
`/chained_orders/<id>` for a CHAINED_ORDER.

## Idempotency

Every WRITE call carries an idempotency key that the client generates fresh per
call. A retry of the SAME call reuses that key, so a network retry never
double-places. Do NOT rely on dedup across *different* keys: two separate place
calls are two separate orders, even if their parameters are identical.

If a WRITE returns `retryable: true` (a write with that key is already in
flight, or its result is briefly unavailable), wait a moment and retry with the
SAME idempotency key -- do NOT mint a new key or start a new order, which would
place a second one. Any other `ok:false` is a terminal reject: fix the inputs
before retrying.

## Reads vs writes

READ tools never change state -- they only observe accounts, markets, and your
existing orders. WRITE tools (place / cancel / pause / resume an order, set
leverage) DO change state. The tools available to you right now, grouped by
capability:

### READ tools

- **`get_balances`** -- Read free / used margin and equity for one or more of the caller's connected exchange accounts. You MUST scope the read: pass EXACTLY ONE of ``account_id`` (a single UUID) or ``account_ids`` (a list of UUIDs) -- not both, and not neither. Reading every account at once is NOT supported (the combined payload is too large). Call list_accounts first to discover account UUIDs. Read-only.
- **`get_order_book`** -- Snapshot top-of-book for ``symbol`` on the account's exchange. Returns top-N bid/ask levels plus derived ``mid``, ``spread``, and ``spread_bps`` so you can sanity-check depth and tightness without recomputing from raw levels. ``symbol`` is required; the venue is resolved from ``account_id``. Read-only; it never places or moves an order.
- **`get_pretrade_analytics`** -- Project what a hypothetical order would look like BEFORE you propose it: expected POV (% of expected volume over the duration), projected price volatility over the window, market-volume realization ratio, and a human-readable ``warning`` advisory (e.g. 'may not complete due to trade limits', 'significant market impact due to high participation rate'). The same engine the manual order-entry UI shows before submit. ``pair``, ``qty`` (base-asset units), and ``duration_minutes`` are required; the venue is the explicit ``exchange`` or the one resolved from ``account_id``. POV > ~2.5% is typically a flag to lengthen the duration. Read-only.
- **`get_leverage`** -- Read the venue's stored leverage (and margin mode when present) for an account on a given pair. Use it to answer 'what's my leverage on X' or to sanity-check the venue side. Returns ``{leverage, margin_mode?, exchange}``. ``pair`` is required; ``account_id`` names the account whose stored leverage is read. Read-only -- use a write tool to change it.
- **`get_pair_max_leverage`** -- Read the venue's MAX allowable leverage for a ``(exchange, pair)`` -- the public cap, not the account's current setting. Use it to pre-validate a requested leverage against the venue ceiling. ``pair`` is required; the venue is the explicit ``exchange`` or the one resolved from ``account_id``. Returns ``{pair, exchange, max_leverage}`` where ``max_leverage`` is ``null`` when no positive cap is on file (treated as unbounded). Read-only.
- **`list_pairs`** -- List tradable pairs on a venue. A VENUE IS MANDATORY -- the catalog is per-exchange, so supply one of: ``exchanges`` (a LIST of venues), ``exchange`` (one venue), or ``account_id`` (resolved to its venue). If you don't know the caller's venues, call list_accounts first, then pass them here as ``exchanges`` to search them all in one call. Pass ``query`` for a FUZZY, typo-tolerant, relevance-ranked name/ticker search (e.g. 'spacex' surfaces 'xyz_SPCX'); pass ``base_asset`` for an EXACT ticker match; ``market_type`` narrows to spot / perp / future / option; ``filter`` is a shell-glob scope on the canonical pair. Each row is ``{pair, base_asset, market_type, exchange}``. Read-only.
- **`list_accounts`** -- List the caller's exchange accounts as ``{id, name, exchange, tier}``. Use it to resolve an account_id from an exchange or nickname without demanding a raw UUID. ``tier`` is the per-account agent permission: ``"trade"`` = fully tradeable; ``"view"`` = READ-ONLY. Read-only.
- **`list_orders`** -- List the caller's LIVE orders, multi-orders, and chained orders -- every non-terminal target. 'Live' is the open status set: SUBMITTED / ACTIVE / FINISHER / PAUSED / SCHEDULED (plus a multi-order's CLEANING_UP); terminal orders (COMPLETE / CANCELED / EXPIRED) are excluded. Bounded to orders CREATED in roughly the last 30 days -- an order live but older than that will not appear. By default returns all THREE kinds: single orders (``target_kind=ORDER``), multi-leg parents (``target_kind=MULTI_ORDER``, e.g. MM / DN / batch), and chained orders (``target_kind=CHAINED_ORDER``, a sequential chain of single orders run in priority order). A multi-order's OR chained-order's child LEGS are excluded FROM THIS ENUMERATION so a leg never shows up as a standalone ORDER row here -- but the exclusion is about enumeration, not addressability: a leg's own id passed DIRECTLY to the by-id reads (get_order_details / get_order_stats / get_working_orders) still resolves as an ORDER. Pass ``kinds`` to scope to one table (e.g. ``['MULTI_ORDER']`` for parents only, ``['CHAINED_ORDER']`` for chains only). Set ``include_child_legs=true`` to ALSO surface those child legs (multi-order AND chained-order legs) as ORDER rows (rarely needed). Each row is a snapshot dict tagged with ``target_kind`` plus ``id`` / ``pair`` / ``status``; feed a row's ``id`` + ``target_kind`` into get_order_stats / get_working_orders / get_recent_fills / get_sibling_orders to drill in. For TERMINAL (completed / canceled / expired) orders use get_order_history. Owner-scoped -- you only ever see your own orders. Read-only.
- **`get_order_history`** -- The caller's RECENT orders, multi-orders, and chained orders, most-recent-first and BOUNDED -- the read for TERMINAL history (completed / canceled / expired) that list_orders (LIVE only) won't show. Each row is the same snapshot dict shape (tagged ``target_kind`` + ``id`` / ``pair`` / ``status``) so a row feeds straight into get_order_stats / get_order_details. Filter with ``kinds`` (default all three: ORDER / MULTI_ORDER / CHAINED_ORDER), ``statuses`` (e.g. ``['COMPLETE','CANCELED','EXPIRED']`` for closed-only; omit for all recent), ``pair`` (exact -- NOTE: a ``pair`` filter excludes chained orders, which have no single pair), and ``after`` / ``before`` (ISO 8601 created_at bounds). ``limit`` is clamped 1..100 (default 20); page with ``page`` (>= 1). Returns ``{orders, page, limit, has_more}``. Any terminal order is also readable by id via get_order_details / get_order_stats. Owner-scoped -- you only ever see your own orders. Read-only.
- **`get_order_stats`** -- Cheap, fixed-size execution summary for ONE order: status, executed qty / notional, fill / fee totals, and last-fill timestamp -- the headline 'where is this order at' numbers without paging through every fill. UNITS: ``executed_qty_total`` is denominated in the order's SELL token -- for a BUY that is the quote/notional currency (so it equals ``executed_notional_total``), for a SELL it is the base asset; ``executed_notional_total`` is ALWAYS the quote/cash value; ``order_qty`` is the order's TARGET token. So on a BUY do NOT divide ``order_qty`` by ``executed_qty_total`` (different currencies) -- gauge fill progress with ``executed_notional_total``, and for the base quantity or fill price use get_recent_fills (each fill carries ``executed_price``; base = ``executed_notional / executed_price``). For a MULTI_ORDER the parent ``executed_qty_total`` sums each leg's sell-token qty and may mix currencies across legs -- read the per-leg ``children``. For a CHAINED_ORDER it returns the same parent totals plus a priority-ordered ``legs`` list (each with its own qty/notional/status) and a ``current_leg`` cursor; the parent ``executed_qty_total`` can likewise mix currencies across legs. ``target_kind`` + ``target_id`` are required (get them from list_orders). For per-fill detail use get_recent_fills. Owner-scoped. Read-only.
- **`get_order_pnl`** -- PnL for ONE MULTI_ORDER run (an MM / DN bot run): ``pnl`` (net), ``realized_pnl``, ``unrealized_pnl``, plus ``fees`` and ``executed_notional`` -- the same headline the Tread.fi bot-run history table shows, which get_order_stats / get_order_history do NOT carry (those return fees only). For a TERMINAL run the numbers are the values captured at completion; for a LIVE run they are computed on the fly, and ``terminal_at`` is null (non-null once captured) so you can tell a cached final PnL from a live sample. All amounts are quote/cash (USD-equivalent). PnL is a MULTI_ORDER-level concept: ``target_kind`` MUST be MULTI_ORDER -- a single ORDER or CHAINED_ORDER target is rejected (they carry no run-level PnL capture). ``target_kind`` + ``target_id`` are required (get the MULTI_ORDER id from list_orders / get_order_history). Owner-scoped. Read-only.
- **`list_mm_orders`** -- The caller's market-maker (MM) bot runs, newest first -- the SAME feed the Tread.fi MM history table renders, so ONE call reads a run end-to-end. Each row is the full run shape with its child leg orders embedded INLINE (no get_order_stats call per bot) PLUS the run-level headline the generic order reads omit: PnL under ``on_complete_stats`` (net / realized / unrealized), ``failure_reason`` (distinguishes a stop-loss vs take-profit vs cancelled exit), the strategy knobs (``alpha_tilt``, ``exposure_tolerance``, ``schedule_discretion``, ``limit_price_spread``, ``order_condition``, ``spread_bps``, ``reference_price_type``), ``repeat_config``, ``pct_filled``, ``fee_asset``, ``leverage`` / ``margin``, ``duration`` and ``schedule_id`` (the OrderSchedule that spawned the run, null for an unscheduled bot -- pass it to cancel_schedule to stop the chain, not just this run). Envelope: ``market_maker_orders`` (the rows) + ``count`` / ``num_pages`` / ``page_number`` / ``page_size`` + a lifetime ``executed_notional`` / ``fees`` totals block. Page with ``page`` + ``page_size`` (max 50) or walk history with the ``after`` / ``before`` created-at cursors; ``statuses`` filters by leg status and ``active_only`` limits to live runs. For a DN run use list_orders / get_order_history; for a single order's execution detail use get_order_stats. Owner-scoped (your own runs plus runs on accounts you can view). Read-only.
- **`list_schedules`** -- The caller's order SCHEDULES, newest first -- the rows behind the web UI's schedule tab. A schedule (created by place_mm_order with ``start_datetime`` and/or ``repeat_count``) is the template that re-places a bot when it fires: canceling a live bot with cancel_order does NOT stop its schedule -- the next iteration still fires. Use THIS read to see what will fire, then cancel_schedule to stop it. Each row: ``schedule_id``, ``pair``, ``status`` (pending = still firing / completed / canceled / failed), ``scheduled_start_time`` (next daily fire time; null for on_complete chains, which fire when the previous run completes), ``schedule_kind`` (once / daily), ``schedule_type`` (market_maker / delta_neutral), ``trigger_type`` (daily / on_complete), ``iterations`` (fired / total), ``per_iteration`` outcomes with each run's ``multi_order_id``, ``trigger_order_id``, and the schedule tab's config columns -- ``mode`` (reference_price_type / engine_passiveness / directional_bias), ``spread`` (spread_bps / reference_exchange) and ``accounts`` (display names, resolve via list_accounts). list_mm_orders rows echo ``schedule_id`` so a live bot can be traced back to its schedule. Filter with ``active_only`` (only still-firing rows), ``status``, ``schedule_type`` or ``trigger_type``; page with ``page`` + ``page_size`` (max 50). Owner-scoped: only the caller's own schedules. Read-only.
- **`get_working_orders`** -- The working child OMS orders UNDER a given target -- the legs a MULTI_ORDER parent is currently working, the single order itself for an ORDER target, or a CHAINED_ORDER's legs in execution-``priority`` order (each row carries that ``priority``). Returns each leg's entry shape (limit_price, buy/sell token amounts, status) -- for execution progress use get_order_stats. ``target_kind`` + ``target_id`` are required (get them from list_orders). Owner-scoped. Read-only.
- **`get_recent_fills`** -- Recent fills under a given target, newest first -- per-fill detail (price, qty, fee, timestamp) for an order, multi-order, or chained order (across all its legs). UNITS: ``executed_qty`` is denominated in the order's SELL token (for a BUY that is the quote/notional currency; for a SELL it is the base asset), while ``executed_notional`` is ALWAYS the quote value -- recover the base quantity as ``executed_notional / executed_price``. ``target_kind`` + ``target_id`` are required (get them from list_orders); ``limit`` caps the rows (default 20). For just the headline totals use get_order_stats. Owner-scoped. Read-only.
- **`get_sibling_orders`** -- Sibling orders of a target -- siblings, not children. For an ORDER target: its TP / SL exit legs. For a MULTI_ORDER target: the MM cleanup or DN closing leg. For a CHAINED_ORDER target: the TP / SL exit legs of EACH chain leg, each tagged with ``entry_leg_id`` / ``entry_leg_priority`` (the chain's own legs are children -- read them via get_order_stats). Each row carries a ``kind`` discriminator (take_profit / stop_loss / dn_closing / ...). ``target_kind`` + ``target_id`` are required (get them from list_orders). An empty list means nothing is attached. Owner-scoped. Read-only.
- **`get_order_details`** -- Load ONE of the caller's orders behind a tread.fi link (or a bare id) and return its details. Use this whenever the user pastes an order URL like ``https://app.tread.fi/multi_order/<uuid>`` or ``https://app.tread.fi/order/<uuid>``, or names a specific order id, and asks what it is / how it did / what's in it. Pass the WHOLE thing in ``ref`` -- full URL, path, or raw UUID; the id is stripped out for you and the ``/order/`` vs ``/multi_order/`` segment selects the right kind (a bare id is probed across kinds). Returns parent scalars (pair(s), side, status, executed / target notional, strategy, leverage, ...) plus a per-leg summary. Set ``include_fills=true`` to also attach recent fills (ORDER / MULTI_ORDER only). Owner-scoped: another user's order resolves to 'order not found'. Read-only.
- **`list_competitions`** -- List trading competitions visible to the caller. Each row is ``{slug, title, venue, coin_filter, status, window_start_ms, window_end_ms, epoch_hours, prize_note, entered}`` -- ``entered`` says whether the caller has signed up. Pass a row's ``slug`` to get_competition_board for the standings. Read-only.
- **`get_competition_board`** -- One competition's leaderboard: the top 25 of each race (points / live volume / live PnL) plus the caller's own row. Each row carries ``ranks`` -- its full-population rank per race (a null pnl rank means that row is not in the PnL race this epoch) -- ``points``, cumulative ``volume``, live ``volume_today``, and ``daily_return``. ``board.epochTop`` holds per-epoch top-10 history; ``you.address`` is the caller's entry address (row addresses are redacted). ``slug`` is required -- discover slugs with list_competitions. Read-only.

### WRITE tools

- **`place_order`** -- Place a single live order on one of the caller's TRADE accounts. This is a WRITE that moves real money -- size it yourself and monitor it; nothing on the MCP side manages the position after it lands. Required: ``account_id`` (a TRADE account from list_accounts), ``pair`` (canonical ``BASE[:VARIANT]-QUOTE`` from list_pairs), ``side`` (buy/sell), and EXACTLY ONE quantity frame (``base_asset_qty`` / ``quote_asset_qty`` / ``target_order_qty``). Size with get_pretrade_analytics first. The order is scoped to the caller's own eligible accounts -- a foreign account is rejected. Every call requires a fresh idempotency key; a retry reusing it returns the first result instead of double-placing.
- **`place_mm_order`** -- Place a market-maker (MM) bot order on ONE of the caller's TRADE accounts: a two-leg buy+sell spread that continuously quotes around a reference price for ``duration_minutes``. Size it with ``notional_usd`` (total volume worked) OR ``margin_usd`` (collateral locked; notional = margin * leverage * 20). Quoting mode is ``reference_price``: ``mid`` (symmetric around mid), ``grid`` / ``reverse_grid`` (laddered), ``dynamic_grid`` (a self-driving grid that auto-tunes its spread from realized vol), ``blend`` (mid blended with a reference venue -- requires ``reference_exchange``), or ``signal`` (quote tracks an RSI signal -- requires ``signal_name``). Risk exits: ``stop_loss_pct`` defaults to 10, ``take_profit_pct`` is OFF unless passed -- set both to reproduce a web-UI config. This is a WRITE that moves real money. The order is scoped to the caller's own eligible accounts -- a foreign account is rejected. Optionally SCHEDULE or REPEAT the session (same semantics as the web MM form): ``start_datetime`` delays the (first) run to an ISO-8601 time; ``repeat_count`` (1-20) with ``repeat_trigger='on_complete'`` (the default) re-runs back-to-back -- each next run starts when the previous completes -- while ``repeat_trigger='daily'`` runs once per day at the ``start_datetime`` clock time (daily REQUIRES ``start_datetime``). A scheduled placement (``start_datetime`` set) returns a schedule_id, NOT an order: it won't appear in list_mm_orders until it fires -- inspect it with list_schedules and stop it (plus any live session) with cancel_schedule. Every call requires a fresh idempotency key; a retry reusing it returns the first result instead of double-placing. Pairs are canonical ``BASE[:VARIANT]-QUOTE`` (resolve via list_pairs); accounts are TRADE accounts from list_accounts.
- **`place_dn_order`** -- Place a delta-neutral (DN) bot order: a two-leg pair-trade that BUYs ``long_pair`` on one of the caller's TRADE accounts and SELLs ``short_pair`` on another, worked in via TWAP over ``duration_minutes``. The two legs are usually the same asset family across two venues (the funding-divergence premise of DN). ``notional_usd`` is the total two-leg notional, split 50/50. Optionally auto-unwind: ``position_duration_minutes`` (max hold before the closing order fires) and/or ``dn_stoploss_percent``. This is a WRITE that moves real money. The order is scoped to the caller's own eligible accounts -- a foreign account is rejected. Every call requires a fresh idempotency key; a retry reusing it returns the first result instead of double-placing. Pairs are canonical ``BASE[:VARIANT]-QUOTE`` (resolve via list_pairs); accounts are TRADE accounts from list_accounts.
- **`place_multi_order`** -- Place a GENERAL multi-order on the caller's TRADE accounts: ONE parent order wrapping N child orders that execute together, all sharing the algo config you pass at the top level (strategy / duration / shaping knobs). Each ``legs`` entry becomes a child order with its own pair / side / quantity (and optional per-leg account override -- otherwise the top-level ``account_id`` applies). Use this to fan one execution intent across legs at once (e.g. TWAP-buy ETH and SOL over an hour) without placing each separately. A multi-order is the lower-level OMS construct; the market-maker (MM) and delta-neutral (DN) BOT PRODUCTS built on it have their own dedicated tools -- use place_mm_order / place_dn_order for those, NOT this. A WRITE that moves real money; scoped to the caller's own accounts -- a foreign account on any leg is rejected. Every call requires a fresh idempotency key; a retry reusing it returns the first result instead of re-placing.
- **`place_chained_order`** -- Place an ORDERED chain of single orders. The OMS runs the legs strictly in array order -- each leg auto-starts once the previous one completes (sequencing is automatic; never gate a leg on the prior leg's fill via ``order_condition``). Pass ``legs=[{account_id, pair, side, <qty>, strategy, ...}, ...]`` -- 2 to 10 heterogeneous legs. A typical use is an open leg followed by a conditional ``reduce_only`` exit leg. This is a WRITE that moves real money; every leg's account is scoped to the caller's own accounts -- a foreign / unknown account on any leg rejects the whole chain. Every call requires a fresh idempotency key. For a SINGLE order use place_order; for a simultaneous multi-pair fan-out use place_multi_order.
- **`cancel_order`** -- Cancel one of the caller's live orders. Keyed by ``target_kind`` (ORDER / MULTI_ORDER / CHAINED_ORDER) + ``target_id`` -- get both from list_orders. For a CHAINED_ORDER the whole chain is unwound; for a MULTI_ORDER the parent and its legs. A WRITE: owner-scoped (a foreign id resolves to a non-leaky 'not found'), and every call requires a fresh idempotency key.
- **`cancel_schedule`** -- Stop one of the caller's market-maker SCHEDULES -- the MCP equivalent of the schedule tab's X. The composite kill switch: cancels the schedule FIRST (so no next iteration fires mid-teardown), THEN cancels any live MultiOrder session(s) it spawned, reduce-only-flattening residual exposure. This is the right tool when cancel_order alone doesn't stick because the schedule re-places the bot: get the ``schedule_id`` from list_schedules (or the ``schedule_id`` echoed on list_mm_orders rows / returned by a scheduled place_mm_order) and cancel it here. A session that is ALREADY draining is left to finish flattening (cancelling a drain abandons it and strands the residual) and reported under ``skipped_cleaning_up`` -- that is a success, do NOT cancel_order it. Returns the structured stop report (``schedule_cancelled`` / ``orders_cancelled`` / ``skipped_cleaning_up`` / ``residual_flattening_engaged`` / ``residual_remaining``). Idempotent and safe on an already-terminal schedule -- it still sweeps any live session left quoting. Only ``market_maker`` schedules; a delta_neutral schedule is rejected (its positions manage their own lifecycle -- cancel those orders directly). A WRITE: owner-scoped (a foreign id resolves to a non-leaky 'not found'), and every call requires a fresh idempotency key.
- **`pause_order`** -- Pause one of the caller's live orders so it stops working. Keyed by ``target_kind`` (ORDER / MULTI_ORDER / CHAINED_ORDER) + ``target_id`` -- get both from list_orders. Resume later with resume_order. A WRITE: owner-scoped (a foreign id resolves to a non-leaky 'not found'), and every call requires a fresh idempotency key.
- **`resume_order`** -- Resume one of the caller's paused orders. Keyed by ``target_kind`` (ORDER / MULTI_ORDER / CHAINED_ORDER) + ``target_id`` -- get both from list_orders. The inverse of pause_order. A WRITE: owner-scoped (a foreign id resolves to a non-leaky 'not found'), and every call requires a fresh idempotency key.
- **`set_leverage`** -- Set the venue's stored leverage for one of the caller's accounts on a given pair. Required: ``account_id`` (a TRADE account from list_accounts), ``pair`` (canonical ``BASE[:VARIANT]-QUOTE``), and ``leverage`` (the target multiplier). The account is owner-scoped -- a foreign account is rejected as 'account not found'. The venue may decline the change when a position is open; the result reports the effective leverage and whether it changed. A WRITE: every call requires a fresh idempotency key.
